# 0.1.0-beta.2 verification

Release date: October 10, 2026. This beta adds audience segments and page rules
for visual builders and closes two fail-open paths. The npm beta and matching
sandbox archive are built from the same source revision. The EmDash plugin
directory remains unpublished.

## What this beta adds

- **Fail-closed caller plans.** In stripe mode, an access check whose caller
  requires an unknown or removed plan now denies access, even beside a
  configured plan. Before, the unknown plan was dropped and access could be
  granted. Off and delegate modes pass the plans through unchanged.
- **Route-cache opt-out.** HTML and every other `no-store` response, including
  paid agent Markdown and account redirects, now opt out of Astro's route cache.
  A page hint or a configured route rule can no longer store such a response and
  replay it, for example a paid agent read to an unpaid agent. Sites without a
  cache provider are unaffected.
- **`segments()` for visual builders.** `Astro.locals.paidAccess.segments({ entry? })`
  returns `member`, `plan:<slug>` for each owned plan, and `entitled` when the
  entry may render. It makes one entitlement check per request and returns `[]`
  when anything can't be verified.
- **Page rules on the Rules page.** **Paid Access Rules → Add a rule for a page**
  adds a members-only rule for a published entry you edit outside EmDash's
  standard editor, such as a page built in a visual builder's own canvas. Page
  rules restrict people only and are never sold to AI agents; in stripe mode
  each one needs at least one plan. The form only adds a rule, never overwrites
  one. A page rule takes effect only when the site's route for those pages
  checks Paid Access.
- **A [visual builders guide](../guides/visual-builders.md)** covers the segment
  vocabulary and its failure behavior by mode, host recipes, teasers, whole-page
  rules, caching duties, delegate-mode limits, and pricing without a plans mirror.

Settings also refuse a new or renamed plan ID that can't form a `plan:<slug>`
segment; plans saved earlier still load. The [changelog](../../CHANGELOG.md)
lists every change.

## Local checks

- Node 22.23.3, pnpm 12.10.1, EmDash/x402 1.2.0 and Astro 7.3.5.
- The release gate (`pnpm release:check`) passed on the release source: peer
  compatibility, TypeScript, build, manifest and bundle validation, and package checks.
- 227 unit/component/route tests and four real EmDash/workerd sandbox tests passed.
  The default suite skips the opt-in settlement test.
- Both fixes have regression tests that fail on the 0.1.0-beta.1 source.

## Review

Each commit in this beta had an independent adversarial review, and the three
main code commits had a second independent review; the final small fix was
reviewed directly. Findings were applied before
release. Review made the page form add-only and people-only, and made
`segments()` return `[]` on any unverifiable answer. A later docs accuracy
review led to the stripe-mode plan requirement for page rules.

## Not repeated for this beta

The fresh-consumer installation, the deployed-site acceptance and the Base
Sepolia settlement test recorded for [0.1.0-beta.1](0.1.0-beta.1.md) were not
repeated. Two changes touch the runtime paths those checks covered, and unit
tests cover both:

- the middleware's route-cache opt-out, which does nothing on a site without a
  cache provider; and
- the stripe-mode access check, which behaves as before for callers that pass
  only configured plans or none.

`segments()`, its private entitlements route and page rules are new and have
not been exercised on a deployed host.

## Known limits

- In stripe mode, a saved rule that names a plan removed later drops that plan
  when the rule is read. Its other plans still grant access, and a rule left
  with no configured plan denies everyone. Unknown plans from a caller now fail
  closed; stored rules don't yet. Review rules after removing a plan.
- If a member's stored Stripe customer no longer exists in Stripe, for example
  after a site switches Stripe accounts, `segments()` returns `[]` for that
  member on every request until the stored record is fixed. Access checks still
  fall back to an email search.
- The page form lists only the 100 newest published entries of a collection,
  with no search.
- No visual builder publishes the builder-side entry point for `segments()` yet;
  the guide's recipes use placeholder names.

The [0.1.0-beta.1 limits](0.1.0-beta.1.md#limits-of-this-evidence) still apply.
